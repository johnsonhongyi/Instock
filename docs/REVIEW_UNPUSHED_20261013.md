## 发现的问题与修复

### 1. 数据查询请求参数直接拼接 SQL

- 日期、列筛选、分页及排序参数原先参与 SQL 字符串拼接，既有代码存在 SQL 注入和越界异常风险。
- 将请求值统一改为数据库绑定参数，表名与列名仅来自现有模块元数据；排序方向只允许 ASC/DESC，并校验列索引、分页和查询模块。
- 非法参数返回 HTTP 400；保留接口参数、响应结构、缺表空结果、DataTables draw、多列排序和不分页模式，同时修复日期作为第二筛选项时使用 `==` 的错误。

### 2. 历史补采被收盘时间门禁挡住

- 原先先检查“当日收盘后”，导致历史快照缓存也无法读取，新增的历史补采实际上不能完成工作。
- 调整为优先读取已有历史缓存，再限制实时抓取。大宗交易使用真实日期范围接口，允许回补过去日期，当日和未来日期仍受原有收盘判断保护。
- 分红和资金流不使用当前结果伪造历史快照，只恢复已有历史缓存；无法安全恢复的新日期不会阻塞更早、具备真实历史来源的数据恢复。

### 3. 异常状态文件可能中断恢复流程

- 状态文件若为 JSON 数组，或者 status 为数组等非字符串，原逻辑可能抛出属性或集合查找异常。
- 对状态对象和字段类型显式检查，忽略异常内容；单个数据集恢复异常不会阻断同批其他数据集。
- blocked/deferred/failed/started 状态可按既有共享锁、缓存和供应商冷却策略受控重试；每轮仍仅处理最近一个可恢复历史日期。

### 4. 并发扫描统计可能导致误删历史策略结果

- 批量日期任务使用线程池，而零结果清理依赖模块共享的 `_last_scan`。其他日期的完整零结果统计可能覆盖失败日期统计，导致错误清理。
- 清理与阶段记录改用当前线程独立的扫描统计；保留既有函数签名和全局最近统计兼容性。
- 只有非空输入、完整覆盖、匹配为零、错误明确为零且表存在时，才删除该日期旧结果；失败、不完整或空输入均保留已有行。

### 5. 交易日测试依赖本机环境

- 旧测试仍模拟已不再使用的交易日数据源，结果会受本机是否安装 TK 日历影响。
- 测试改为模拟当前 TK 适配器接口，不改动实际交易日业务逻辑，也不读取或修改真实日历。
